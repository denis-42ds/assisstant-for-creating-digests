# HANDOFF — ИТ/ИБ-Дайджест (Codenrock, задача 2)

Версия: v1.0 (зафиксировать git-тегом перед записью видео/подачей)
Обновлено: 03.10.2026, чат «Разработка»

## Что реализовано

Рабочий end-to-end пайплайн: сбор публикаций → предфильтр по профилю
интересов (TF-IDF) → дедупликация (схлопывание публикаций об одном
событии) → разметка через LLM (категория/вес или теги + готовый текст,
таксономия — из файла-образца организаторов) → рендер в Markdown.

Архитектура — вариант B из брифа, все 5 ступеней реализованы:

1. `sources.yaml` + `tools/fetch_corpus.py` — сбор корпуса из RSS
   (feedparser), с fallback-заголовками против WAF-блокировок
   (`tools/_http.py`). `tools/check_feeds.py` — независимая проверка
   доступности источников.
2. `pipeline/prefilter.py` — TF-IDF-предфильтр (scikit-learn).
   Однословные keywords/tech_stack профиля — в общем векторном
   пространстве; многословные keywords/topics — отдельным бонусом за
   точное совпадение фразы (см. ограничение №4).
3. `pipeline/dedup.py` — дедупликация по TF-IDF-косинусу + защита по
   CVE-номерам (не пересекаются → не сливать) + минимум общих значимых
   слов + окно дат (±2 дня).
4. `pipeline/llm_stage.py` — разметка батчами через переключаемый
   LLM-бэкенд (`claude`/`ollama`/`gemini`/`openrouter` — `LLM_BACKEND`
   в `.env`, без правки кода).
5. `pipeline/render.py` — рендер в Markdown, формат под аудиторию
   (tech: группировка по категории/весу; manager: список с готовым
   текстом и тегами).
6. `cli.py` — точка входа, гоняет весь пайплайн одной командой, печатает
   демо-метрики (сколько источников рабочих, публикаций на входе,
   отсеяно предфильтром, слито как дубли, LLM-бэкенд, итог в дайджесте).
7. `app.py` — веб-интерфейс (Streamlit): «готовые результаты» (мгновенно,
   без LLM) и «живой запуск» (с теми же демо-метриками на экране и
   rate-limit'ом на публичный трафик). Публикуется через ngrok со своей
   машины (решение от 30.09 — не managed-хостинг).

## Команды запуска

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
# впиши ключ нужного бэкенда в .env (см. README.md) и поставь LLM_BACKEND

python tools/check_feeds.py                      # проверка источников
python tools/fetch_corpus.py --per-source 20      # сбор корпуса

python cli.py --profile profiles/soc_analyst.yaml
python cli.py --profile profiles/devops_engineer.yaml
python cli.py --profile profiles/it_director_ciso.yaml
# -> output/<профиль>-<версия корпуса>.md
```

Для локального бэкенда (обязателен на финальной проверке организаторами,
Q&A 30.09):
```bash
ollama pull qwen3.6:35b-a3b
export OLLAMA_CONTEXT_LENGTH=22000
ollama serve
# в .env: LLM_BACKEND=ollama
```

## Проверено на реальных данных (не только на синтетике)

- **prefilter:** персонализация подтверждена — три профиля дают заметно
  разные подборки на одном корпусе (SOC — CVE/эксплойты/KEV, DevOps —
  Kubernetes/CI/CD/GitLab, CIO — 152-ФЗ/регуляторика/бизнес-риски)
- **dedup:** настоящие дубли (одна новость у двух источников, напр.
  «Додо Пицца» у xakep и anti_malware) схлопываются; шаблонные заголовки
  одного источника (CISA "Adds Two Known Exploited Vulnerabilities...")
  — НЕ схлопываются ложно, несмотря на то что по голому косинусу они
  похожи сильнее настоящих дублей (0.826 против 0.498 — см. комментарии
  в коде dedup.py)
- **llm_stage + cli.py + render.py:** полный путь от корпуса до
  готового `.md`-файла подтверждён вживую с реальным LLM-бэкендом
  (Gemini, gemini-3.5-flash-lite) на всех трёх профилях
- **app.py:** бизнес-логика (загрузка профилей/корпуса, rate-limit,
  полный прогон пайплайна) протестирована отдельно от UI; Streamlit-
  сервер поднимается и отвечает HTTP 200 без ошибок в логе — живое
  взаимодействие с виджетами в браузере не проверялось (см. ограничения)

## Ограничения (сознательные, не баги)

1. **Нет живого сбора из Telegram.** Категория «Инфо» в таксономии
   организаторов жёстко привязана к источнику («вес = Новости ТГ»); у
   нас нет живых TG-источников, LLM использует «Инфо» как общую
   категорию для некритичных новостей. Осознанно не исправляли.
2. **Нет полного структурного извлечения полей Dataset 1.** Для
   технарей не извлекаем все 8–10 полей организаторов (атакующая
   группировка, страна жертвы, CVSS-вектор, IOC и т.п.) — только
   категория/вес/краткое объяснение. Решение от 02.10: сначала рабочий
   концепт, детали — если останется время.
3. **Нет сжатия в «месячную выжимку» для менеджера** (отдельный
   LLM-проход из архитектуры брифа) — менеджер получает тот же плоский
   список, что и технарь, в другом формате (готовый текст + теги на
   публикацию), без агрегации по темам в единый текст.
4. **Дедупликация:** защита от ложных слияний по CVE работает только
   для публикаций про уязвимости; для прочих категорий — только окно
   дат + минимум общих слов, не абсолютная гарантия.
5. **securitylab.ru и cisoclub.ru недоступны** (см. выше) — покрытие
   деловой прессы держится в основном на kommersant.ru.
6. **LLM-разметка не детерминирована** — одна и та же публикация может
   получить немного разный вес/теги между прогонами (нормально для LLM,
   не баг пайплайна).
7. **Доступность сервиса зависит от ноутбука** — ссылка живёт через
   ngrok с личной машины, не managed-хостинг. Нужен закреплённый
   static-домен в ngrok (не меняется при перезапуске), отключённый сон
   ОС и в идеале супервизор процесса на время проверки экспертами.
   Веб-интерфейс (`app.py`) и UI-взаимодействие (клики, выбор профиля)
   проверены не до конца — Streamlit-сервер поднимается и отвечает
   HTTP 200 без ошибок в логе, но содержимое виджетов рендерится через
   WebSocket и не проверялось вживую браузером из песочницы.
8. **Экспорт только в Markdown** — DOCX не делали (бриф допускает
   Markdown ИЛИ DOCX, формальное требование закрыто).
